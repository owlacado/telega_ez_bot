# Render deployment: one Web, one worker, one TEST PostgreSQL

This is deployment preparation for a controlled fictional-technician TEST pilot, not authorization to start live provider acceptance. `render.yaml` declares exactly one Docker Web service, one Docker Background Worker, and one new Render-managed PostgreSQL database. It does not copy or connect to the normal local database. Review the region and plans in the Blueprint before creation; the selected `1c-2g` service and `0.5c-1g` database plans are starting choices, not an approved capacity or cost commitment. Keep each service at one instance.

## Process and network boundary

Render terminates public HTTPS. The Web container exposes only Caddy on `0.0.0.0:$PORT` (Render's default is `10000`). Caddy routes `/api`, `/api/*`, `/docs`, `/docs/*`, `/redoc`, `/redoc/*`, and `/openapi.json` to Uvicorn on `127.0.0.1:8000`; all other traffic goes to the full Next.js standalone server on `127.0.0.1:3000`. Neither application port is published. Caddy does not terminate TLS, strips inbound `Forwarded` and `X-Forwarded-*` headers before both upstreams, limits request bodies to 1 MB, and sets 15-second request-header/body read timeouts. Uvicorn disables proxy-header interpretation; Host and Origin validation use the exact public origin. Caddy's reverse proxy streams responses and supports upgraded connections; the current application has no SSE/WebSocket route to exercise directly. The public `/api/health` checks the API and database. `/login` alone is not aggregate health.

The worker image starts one supervisor. It runs one child for each enabled feature: Telegram polling/outbox, schedule delivery, and Google accounting mirrors. A disabled feature starts no child. SIGTERM fans out to every running child; an unexpected exit fails the group, and Render can restart the single worker. The database still owns queue claims, leases, offsets, heartbeats, and retry state. Do not scale the combined worker above one instance for this pilot.

Both services receive `RENDER_DATABASE_URL` from the Render PostgreSQL **internal** connection string. The entrypoint converts its `postgresql://` scheme to SQLAlchemy's `postgresql+asyncpg://` and sets `DATABASE_URL` in-process. On Render it refuses loopback, Compose, and test-db hosts. The PostgreSQL resource has no public IP allowlist. There is no PostgreSQL process or persistent business data inside either application image.

## Environment inventory

Set the same public origin and provider settings in **both** services. The Blueprint supplies the following non-secret configuration: `APP_ENV=pilot`, `APP_VERSION=0.3.0`, `COOKIE_SECURE=true`, `DEBUG=false`, `ALLOW_FAKE_PROVIDERS=false`, `TELEGRAM_MODE=disabled`, `GOOGLE_MODE=disabled`, and `SCHEDULE_DELIVERY_ENABLED=false`. The worker also sets `PTB_TIMEDELTA=true`. Render supplies `RENDER_GIT_COMMIT`, `RENDER_DATABASE_URL`, and `$PORT` for Web. The entrypoint derives `RELEASE_COMMIT`, `DATABASE_URL`, `ALLOWED_ORIGINS`, and, when Google is enabled, the exact `GOOGLE_OAUTH_REDIRECT_URI` (`PUBLIC_APP_ORIGIN` plus `/api/calendar-connections/google/callback`). Do not set those derived values independently. Fake provider modes and `ALLOW_FAKE_PROVIDERS=true` are rejected at this entrypoint.

Enter `PUBLIC_APP_ORIGIN` manually for both services as the **same exact HTTPS origin** of the Render Web service, with no path or trailing slash. If a custom domain is later added, update both origin variables and the TEST Google OAuth callback registration together, then redeploy both services.

If the Dashboard insists on nonempty optional `sync: false` values, defer those entries until TEST resources are ready; never enter production credentials or sample encryption keys. Review actual values and access controls in Render's secret store before enabling any worker. The chosen service plans, database plan, region, disk/backup policy, and alert route still require operator review.

## Dashboard and release sequence

1. Review and commit this deployment configuration locally, then have the authorized operator publish that reviewed commit to the Git repository connected to Render. This preparation task does **not** push, create Render resources, or invoke providers.
2. In Render Dashboard, create a Blueprint from that repository and `render.yaml`. Confirm the preview contains exactly `technician-hub-test-web`, `technician-hub-test-worker`, and `technician-hub-test-db` in one region. Review plans/costs and keep Web and worker at one instance. Confirm the database is new, empty, private, and uses the internal connection string. Do not import the local database.
3. Supply `PUBLIC_APP_ORIGIN` on both services as the exact assigned HTTPS Web URL. Supply only dedicated TEST secrets when available. Initially leave all provider features disabled. Check that the Render release commit is the reviewed 40-character commit and both services use the same release/configuration. The Web pre-deploy command runs `python -m hub.render_runtime migrate` against the new TEST database; the worker does not migrate.
4. After Web deployment, open the Web service's interactive Shell and run `python -m hub.render_runtime create-manager --username <test-manager-name>`. The command prompts for the password without a CLI argument. Do not use a customer identity. A fresh database has no manager, so preflight correctly reports `BLOCK manager` until this step.
5. In the Web Shell run `python -m hub.render_runtime preflight`; require no `BLOCK`. Check public `https://<web-host>/api/health`, `/login`, and a real manager login. Check the authenticated Operations Health page. In the worker Shell run `python -m hub.render_runtime queues` and confirm disabled workers report `DISABLED`; once a feature is enabled, its worker must report `RUNNING`. Repeat the queue check at least once per minute with alerting according to `PILOT_RUNBOOK.md`.
6. Prepare the dedicated TEST Telegram bot/private chat/group and dedicated TEST Google account/calendar/jobs/Spreadsheet listed in `PILOT_LIVE_ACCEPTANCE_PLAN.md`. Enter their credentials into the Render secret store, switch only the required provider modes on **both** services, redeploy, and complete the live acceptance runbook in order. No live provider step was performed in this preparation.

Runtime startup commands are `python -m hub.render_runtime web` and `python -m hub.render_runtime worker`. An operator can rerun `python -m hub.render_runtime migrate` from the Web image during a controlled release, `python -m hub.render_runtime preflight` from Web, and `python -m hub.render_runtime queues` from either service. To revoke a TEST manager's sessions, run `python -m hub.render_runtime revoke-sessions --username <test-manager-name>` in an interactive Shell. These wrappers always resolve the Render database connection before invoking the existing commands.

It does not itself establish managed backup retention/restores, secret-store recovery custody, worker/queue polling and paging, disk/connection alerts, or a completed provider recovery drill. The local `scripts/backup-postgres.ps1` targets Compose and must not be pointed at the Render database. Configure Render-native/private backups and an isolated restore drill with the approved 30-day policy, then document evidence for TD-012/017/025/029 before the pilot. Follow `PILOT_RUNBOOK.md` thresholds and keep TD-022/027/028/030/033 open until dedicated live TEST acceptance succeeds.
